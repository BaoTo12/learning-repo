# Module 02: Stateless Token Security & Asymmetric Cryptography

Welcome back class. Today we analyze **Stateless Token Security & Asymmetric Cryptography (CS-527)**.

As web applications scale horizontally, querying a centralized session database on every single API request creates severe database performance bottlenecks. To enable distributed microservices, we shift from stateful session models to stateless bearer tokens. The server certifies client identities by writing claims into a signed **JSON Web Token (JWT)**, which downstream resource servers can validate locally using public key cryptography.

Today we study the anatomy of the JWT specification, analyze the differences between symmetric and asymmetric signing algorithms, and write a resilient token generation and validation service in **Java 21** using the **JJWT** library.

---

## 1. Academic Lecture: JWT Specifications & Signatures Math

### 1. Anatomy of a JSON Web Token (RFC 7519)
A JWT is a string composed of three Base64URL-encoded segments separated by dots (`.`):
*   **Header**: Specifies the token metadata, including the token type (`typ: JWT`) and the signing algorithm used (e.g. `alg: RS256`).
*   **Payload**: Contains the statements or claims about the user (e.g. `sub` for subject identity, `exp` for expiration timestamp, `iss` for issuer source, and custom groups or roles).
*   **Signature**: The cryptographic validation block generated by applying the algorithm to the encoded header and payload segments.

### 2. Symmetric (HS256) vs. Asymmetric (RS256) Cryptography
*   **HS256 (HMAC with SHA-256)**: Symmetric signing. The authorization server and all resource servers share the exact same secret key string. Both token generation and token verification use this key. If an attacker compromises a single downstream resource server, they obtain the secret key, allowing them to forge valid tokens.
*   **RS256 (RSA Signature with SHA-256)**: Asymmetric signing. The authorization server holds a **Private Key** (kept secure) to sign tokens. Downstream resource servers only hold the corresponding **Public Key**. Resource servers can verify that a token was signed by the private key, but cannot forge signatures themselves.

### 3. Expiration and Token Rotation Lifecycle
Because stateless tokens cannot be easily revoked before their expiration time, we enforce a dual-token architecture:
*   **Access Token**: Short-lived (e.g. 15 minutes) bearer token containing user roles. Sent on every request.
*   **Refresh Token**: Long-lived (e.g. 7 days) token stored securely (e.g., in a secure database or HttpOnly cookie). Used to request new Access Tokens. If an Access Token is compromised, it expires quickly. If a Refresh Token is suspected of abuse, the database entry is deleted, stopping token renewal.

```text
[Authorization Server]
   ├── Holds Private Key (Secret)
   └── Signs: Header + Payload ──> Generates JWT
                                      │
                                      ▼
[Resource Server] ◀─────── (Client transmits JWT) ──────── [Browser / Client]
   ├── Holds Public Key (Shared)
   └── Verifies: Signature Math ──> Validates claims locally (No DB checks)
```

## 2. Theory vs. Production Trade-offs

When selecting a token signing strategy, weigh algorithm security against parsing complexity:

| Metric / Dimension | Symmetric Signatures (HS256) | Asymmetric Signatures (RS256) | Elliptic Curve Signatures (ES256) |
| :--- | :--- | :--- | :--- |
| **Key Management** | Simple (Single shared string) | Complex (Public/Private PEM keys) | Complex (EC curve key pairs) |
| **Trust Boundaries** | Weak (All nodes can forge tokens) | Strong (Only Auth server can sign) | Strong (Only Auth server can sign) |
| **Verification Speed**| Very Fast (Simple hash check) | Fast (RSA modular exponentiation) | Moderate (Curve multiplication) |
| **Signature Size** | Compact (32 bytes raw) | Large (256 bytes raw) | Compact (64 bytes raw) |
| **Use Case** | Internal monolithic microservices | Cross-domain enterprise APIs | Mobile APIs (reduces payload size) |

## 3. How to Use: Asymmetric Token Engine in Java

Let us write a compile-grade Java 21 implementation that loads an RSA key pair, signs a JWT using the JJWT library, and decodes it using public-key checks.

### A. The Insecure Symmetric Pattern (Anti-Pattern)

Avoid utilizing weak symmetric keys hardcoded inside configuration files or allowing the algorithm header to be bypassed:

```java
package com.security.api.service;

import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import java.nio.charset.StandardCharsets;
import javax.crypto.SecretKey;

public class NaiveTokenService {
    // DANGER: Hardcoding symmetric key strings in class declarations leads to key leakage.
    // If this key is compromised, all downstream services are vulnerable.
    private final String secret = "super_secret_key_that_is_too_short_for_hs256_specifications";

    public String generateToken(String username) {
        SecretKey key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
        return Jwts.builder()
            .subject(username)
            .signWith(key) // HS256
            .compact();
    }
}
```

### B. The Hardened Asymmetric JWT Service (Production Pattern)

Here is the hardened pattern. We write a token manager class that utilizes asymmetric RSA key pairs, enforces RS256 algorithm validation, and parses claims with clock skew compensation.

```java
package com.security.api.service;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.ExpiredJwtException;
import io.jsonwebtoken.Jwts;
import java.security.KeyPair;
import java.security.KeyPairGenerator;
import java.security.PrivateKey;
import java.security.PublicKey;
import java.util.Date;
import java.util.Map;

public class AsymmetricJwtService {

    private final PrivateKey privateKey;
    private final PublicKey publicKey;
    private final String issuer = "https://security-auth-server.com";

    public AsymmetricJwtService() throws Exception {
        // Generate a cryptographically secure 2048-bit RSA key pair
        KeyPairGenerator keyGen = KeyPairGenerator.getInstance("RSA");
        keyGen.initialize(2048);
        KeyPair keyPair = keyGen.generateKeyPair();
        this.privateKey = keyPair.getPrivate();
        this.publicKey = keyPair.getPublic();
    }

    public String generateAccessToken(String subject, Map<String, Object> claims, long durationMillis) {
        Date now = new Date();
        Date expiry = new Date(now.getTime() + durationMillis);

        return Jwts.builder()
            .issuer(issuer)
            .subject(subject)
            .claims(claims)
            .issuedAt(now)
            .expiration(expiry)
            .signWith(privateKey, Jwts.SIG.RS256) // Asymmetric Private Key RS256 signing
            .compact();
    }

    public Claims validateAndParseToken(String jwtToken) {
        try {
            return Jwts.parser()
                .verifyWith(publicKey) // Verify using matching Public Key
                .requireIssuer(issuer)  // Validate token origin issuer claim
                // Compensate for physical clock differences up to 60 seconds
                .allowedClockSkewSeconds(60)
                .build()
                .parseSignedClaims(jwtToken)
                .getPayload();
        } catch (ExpiredJwtException e) {
            throw new SecurityException("Token signature is valid but has expired.", e);
        } catch (Exception e) {
            throw new SecurityException("Invalid JWT signature or parsing failure.", e);
        }
    }
}
```

## 4. Common Errors & Pitfalls

### Pitfall 1: Accepting the "none" Algorithm Header
Allowing JWT library parsers to validate tokens without enforcing signature constraints.
*   **Why it fails**: Attackers can forge tokens by writing a header defining `"alg": "none"`, removing the signature block, and submitting the token. Un-configured parsers decode the header and skip validation, accepting the forged claims.
*   **Mitigation**: Use JJWT's `.verifyWith(publicKey)` or configure Spring Security to explicitly reject tokens lacking valid signatures or using the `none` algorithm.

### Pitfall 2: Storing Tokens in LocalStorage
Saving sensitive bearer tokens inside browser `localStorage` or `sessionStorage`.
*   **Why it fails**: Script code running inside the browser can read local storage. If your app is vulnerable to an XSS injection, attackers can read and steal the token, bypassing security controls.
*   **Mitigation**: Store access tokens strictly in memory, or use secure HttpOnly cookies to restrict script visibility.

## 5. Socratic Review Questions

### Question 1
Why are asymmetric algorithms (like RS256) preferred over symmetric ones (like HS256) in distributed microservice architectures?

#### Answer
In microservices, the verification step runs on multiple independent hosts. If using HS256, every single host must hold the secret signing key. A security compromise of any single microservice exposes the shared secret, compromising the entire network. With RS256, only the core authentication server holds the private signing key. Microservices only hold the public key, which can only verify signatures, not forge them.

### Question 2
What is the purpose of the "clock skew" buffer configuration during token verification?

#### Answer
Physical server clocks are subject to drift (skew) due to virtualization overhead or network synchronization differences. If an auth server issues a token that expires at `12:00:00`, and a resource server's clock runs 5 seconds fast, it will reject a valid token presented at `11:59:57` (from its perspective, it's already `12:00:02`). Setting a skew parameter (e.g., 60s) allows a validation window to compensate for clock differences.
