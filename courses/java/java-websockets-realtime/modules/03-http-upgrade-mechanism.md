# Module 3: HTTP Upgrade Mechanism

A WebSocket connection begins as a standard HTTP request. Rather than defining a completely new port and protocol allocation for WebSockets—which would be blocked by corporate firewalls, proxies, and load balancers—the protocol designers utilized the **HTTP Upgrade Mechanism**. 

This module reviews the mechanics of the upgrade sequence across HTTP/1.1, HTTP/2, and HTTP/3. We will break down the handshake headers, calculate the cryptographic security keys in Java, explore how modern HTTP versions multiplex WebSocket streams, and implement a raw Java socket server to execute the handshake manually.

---

## Learning Objectives
By the end of this module, you will be able to:
1. **Explain the purpose of the HTTP Upgrade Mechanism** and how it transitions a connection from stateless request-response to stateful frame streaming.
2. **Compute the `Sec-WebSocket-Accept` header value** in Java using SHA-1 hashing and Base64 encoding.
3. **Analyze the differences** between WebSocket upgrades in HTTP/1.1 and the extended `CONNECT` bootstrapping mechanism in HTTP/2 (RFC 8441) and HTTP/3.
4. **Deploy security mitigations** against Cross-Site WebSocket Hijacking (CSWSH) by validating origins during the handshake.
5. **Implement a raw Java Socket server** that intercepts, parses, and completes a WebSocket upgrade handshake without external libraries.

## 1. Why the HTTP Upgrade Mechanism Exists

If WebSockets required a new TCP port allocation (e.g. port 8081 or 9000) to establish connections:
- Almost all corporate firewalls and proxies would block the traffic, as they are configured to permit only port 80 (HTTP) and port 443 (HTTPS).
- Security teams would reject exposing additional ports on public web servers.

To bypass this restriction, WebSockets utilize the standard HTTP ports. A client initiates a connection using standard HTTP, and then requests the server to **upgrade** the communication protocol. Once both parties agree, they reuse the already established TCP socket to transmit binary WebSocket frames, bypassing firewall restrictions.

## 2. HTTP/1.1 Handshake Upgrade Flow

Under HTTP/1.1, a client requests a protocol switch by sending specific upgrade headers.

```
Client                                      Server
  │ ─── GET /chat (Upgrade: websocket) ───► │
  │ ◄─── HTTP/1.1 101 Switching Protocols ─ │ (Protocol swapped to binary framing)
```

### The Client Request Headers:
```http
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: http://example.com
Sec-WebSocket-Protocol: chat, superchat
```

#### Key Header Explanations:
1. **`Upgrade: websocket`**: Tells the server the client wishes to switch the protocol to the WebSocket protocol.
2. **`Connection: Upgrade`**: Instructs intermediate proxies not to close the connection after the response is completed, but to keep the underlying socket active for the upgraded protocol.
3. **`Sec-WebSocket-Key`**: A random, Base64-encoded 16-byte value generated by the client. It is used by the server to prove it understands the WebSocket protocol.
4. **`Sec-WebSocket-Version: 13`**: Defines the protocol version (13 is the standard final version defined in RFC 6455).
5. **`Origin`**: Identifies the origin webpage requesting the connection. Used by the server to prevent unauthorized cross-origin requests.
6. **`Sec-WebSocket-Protocol`**: (Optional) A comma-separated list of subprotocols (e.g. `STOMP`, `MQTT`, `WAMP`) the client supports, allowing the server to select one.

### The Server Response Headers:
If the server accepts the upgrade, it responds with:
```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: chat
```

#### Key Header Explanations:
1. **`HTTP/1.1 101 Switching Protocols`**: The standard status code indicating the server is switching to the protocol requested in the `Upgrade` header.
2. **`Sec-WebSocket-Accept`**: The server's cryptographic proof validating the client's `Sec-WebSocket-Key`.
3. **`Sec-WebSocket-Protocol`**: Confirms the specific subprotocol selected by the server (e.g. `chat`).

## 3. Sec-WebSocket-Key to Sec-WebSocket-Accept Mechanics

The `Sec-WebSocket-Accept` header is not designed for client authentication or encryption; its sole purpose is to prevent caching proxies and non-websocket servers from mistakenly keeping connections open or caching responses.

### The Cryptographic Formula:
To construct the accept key, the server performs these steps:
1. Read the `Sec-WebSocket-Key` string from the client (e.g., `dGhlIHNhbXBsZSBub25jZQ==`).
2. Concatenate it with the standard RFC 6455 globally unique identifier (GUID):
   $$\text{GUID} = \text{"258EAFA5-E914-47DA-95CA-C5AB0DC85B11"}$$
3. Compute the **SHA-1 hash** of the concatenated string.
4. **Base64-encode** the raw SHA-1 byte digest.

### Java Implementation:
Below is a utility class showing how this computation is executed natively in Java using `java.security.MessageDigest`:

```java
package com.example.realtime.upgrade;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.security.NoSuchAlgorithmException;
import java.util.Base64;

public class WebSocketHandshakeCalculator {

    // Standard RFC 6455 UUID GUID
    private static final String WEBSOCKET_GUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11";

    /**
     * Calculates the Sec-WebSocket-Accept key from the client key.
     */
    public static String calculateAcceptKey(String clientKey) {
        if (clientKey == null || clientKey.trim().isEmpty()) {
            throw new IllegalArgumentException("Client key cannot be null or empty.");
        }

        try {
            // 1. Concatenate key with GUID
            String input = clientKey.trim() + WEBSOCKET_GUID;

            // 2. Initialize SHA-1 MessageDigest
            MessageDigest digest = MessageDigest.getInstance("SHA-1");

            // 3. Compute the raw byte hash
            byte[] hashedBytes = digest.digest(input.getBytes(StandardCharsets.US_ASCII));

            // 4. Encode to Base64 and return
            return Base64.getEncoder().encodeToString(hashedBytes);
        } catch (NoSuchAlgorithmException e) {
            throw new RuntimeException("SHA-1 Algorithm not available in JVM runtime.", e);
        }
    }

    public static void main(String[] args) {
        // Test key from RFC 6455 specification
        String clientKey = "dGhlIHNhbXBsZSBub25jZQ==";
        String expectedAccept = "s3pPLMBiTxaQ9kYGzzhZRbK+xOo=";
        
        String actualAccept = calculateAcceptKey(clientKey);
        
        System.out.println("Client Key      : " + clientKey);
        System.out.println("Expected Accept : " + expectedAccept);
        System.out.println("Actual Accept   : " + actualAccept);
        System.out.println("Validates Match : " + expectedAccept.equals(actualAccept));
    }
}
```

## 4. Upgrading WebSockets on Modern HTTP Versions

While HTTP/1.1 uses connection-level upgrades, modern HTTP protocols (HTTP/2 and HTTP/3) utilize stream-based multiplexing.

### 1. WebSockets over HTTP/2 (RFC 8441)
In HTTP/1.1, a WebSocket connection hijacks the entire TCP socket. If a user opens 6 tabs, they consume 6 TCP connections.

HTTP/2 introduces **RFC 8441**, which bootstraps WebSockets using the **Extended CONNECT Method**:
* **How it works**: Instead of upgrading the TCP connection itself, the client opens a single HTTP/2 TCP connection and requests a WebSocket upgrade on a **single logical stream** inside that connection.
* **The Extended CONNECT Handshake Headers**:
  ```http
  HEADERS (Flags: END_HEADERS)
  :method = CONNECT
  :protocol = websocket
  :scheme = https
  :path = /chat
  sec-websocket-key = dGhlIHNhbXBsZSBub25jZQ==
  sec-websocket-version = 13
  origin = https://example.com
  ```
* **Advantages**:
  - **Single TCP Socket**: Multiple independent WebSocket channels are multiplexed over a single TCP connection.
  - **No Handshake Latency**: Subsequent WebSocket connections do not execute TCP or TLS handshakes, resolving connection setup latency.
  - **Shared Headers**: HPACK compression compresses headers, saving bandwidth.

```
HTTP/1.1 Connection Model
Client  | ─── TCP (Websocket 1) ───► | Server
Client  | ─── TCP (Websocket 2) ───► | Server (Multiple TCP links)

HTTP/2 Multiplexed Model (RFC 8441)
        +----------------------------------------+
Client  | TCP stream 1: Standard REST            |
Client  | TCP stream 3: WebSocket channel 1      | ===► Server (Single TCP link)
Client  | TCP stream 5: WebSocket channel 2      |
        +----------------------------------------+
```

### 2. WebSockets over HTTP/3
HTTP/3 utilizes the **QUIC** protocol, which runs over UDP. WebSockets over HTTP/3 apply the same Extended CONNECT framework defined in RFC 8441:
* The client sends a CONNECT header block over an HTTP/3 stream.
* **No Transport Head-of-Line Blocking**: Since QUIC multiplexes streams at the transport layer, if a packet is lost on WebSocket stream 3, the OS does not halt processing on WebSocket stream 5. This combines the reliability of WebSockets with the performance of UDP-like streams.

## 5. Handshake Validation & Custom Interceptors

Because WebSockets bypass standard HTTP route controllers once established, the handshake phase is the primary security gatekeeper.

### 1. Origin Check (Mitigating Cross-Site WebSocket Hijacking - CSWSH)
Cross-Site WebSocket Hijacking is a CSRF-like vulnerability:
- A user logged into `bank.com` visits a malicious site `evil.com`.
- `evil.com` executes JavaScript opening a WebSocket connection to `bank.com/ws-api`.
- The browser automatically attaches `bank.com` session cookies to the upgrade request.
- If the server accepts the connection without validating the origin, the malicious site gains access to the user's secure WebSocket channel.
- **The Fix**: During the handshake, check the `Origin` header. If it does not match your allowed domain list, reject the upgrade with an `HTTP 403 Forbidden` status.

### 2. Subprotocol Negotiation
If a client requests `Sec-WebSocket-Protocol: STOMP, MQTT`, the server must inspect this list, select one it supports, and return it in the `Sec-WebSocket-Protocol` response header. If no subprotocol matches and the application requires one, the server should reject the handshake.

### Exercise 2: Building a Raw Java ServerSocket Handshake Server
We will implement a standalone Java application that acts as a low-level WebSocket server. It listens on port `9090`, accepts standard HTTP socket connections, parses the upgrade headers, computes the cryptographic accept response, and switches the connection to WebSocket framing.

```java
package com.example.realtime.upgrade.server;

import com.example.realtime.upgrade.WebSocketHandshakeCalculator;
import java.io.*;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.util.Scanner;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class RawWebSocketServer {

    public static void main(String[] args) {
        int port = 9090;
        System.out.println("Starting Raw Socket Handshake Server on port " + port + "...");
        
        try (ServerSocket server = new ServerSocket(port)) {
            while (true) {
                // Wait for an incoming TCP connection
                Socket client = server.accept();
                System.out.println("\n[TCP Connection] Client connected: " + client.getRemoteSocketAddress());
                
                // Process in a fresh thread
                new Thread(() -> handleClient(client)).start();
            }
        } catch (IOException e) {
            System.err.println("Server exception: " + e.getMessage());
        }
    }

    private static void handleClient(Socket client) {
        try (
            InputStream in = client.getInputStream();
            OutputStream out = client.getOutputStream();
            Scanner scanner = new Scanner(in, StandardCharsets.UTF_8.name())
        ) {
            // 1. Read HTTP Request Headers
            StringBuilder requestHeaders = new StringBuilder();
            String line;
            String secKey = null;

            // Read headers until the empty line separating headers from body
            BufferedReader reader = new BufferedReader(new InputStreamReader(in, StandardCharsets.UTF_8));
            while ((line = reader.readLine()) != null && !line.trim().isEmpty()) {
                requestHeaders.append(line).append("\r\n");
                if (line.startsWith("Sec-WebSocket-Key:")) {
                    secKey = line.split(":")[1].trim();
                }
            }

            System.out.println("[HTTP Request Headers Received]:\n" + requestHeaders);

            if (secKey == null) {
                System.out.println("[Handshake Failed] No Sec-WebSocket-Key header found. Closing socket.");
                sendBadRequest(out);
                return;
            }

            // 2. Compute the Accept Key
            String acceptKey = WebSocketHandshakeCalculator.calculateAcceptKey(secKey);
            System.out.println("[Key Computed] Client Key: " + secKey + " -> Accept Key: " + acceptKey);

            // 3. Write HTTP 101 Switching Protocols Response
            String handshakeResponse = "HTTP/1.1 101 Switching Protocols\r\n"
                    + "Upgrade: websocket\r\n"
                    + "Connection: Upgrade\r\n"
                    + "Sec-WebSocket-Accept: " + acceptKey + "\r\n\r\n";

            out.write(handshakeResponse.getBytes(StandardCharsets.US_ASCII));
            out.flush();
            System.out.println("[Handshake Complete] Sent 101 Response.");

            // 4. Send a Basic WebSocket Text Frame
            // A simple unmasked text frame from server to client:
            // Byte 1: 0x81 (FIN = 1, Opcode = 0x1 (Text Frame))
            // Byte 2: Length of payload (Unmasked server frames have Mask = 0)
            String message = "Hello from Raw Java WebSocket Server!";
            byte[] messageBytes = message.getBytes(StandardCharsets.UTF_8);
            
            out.write(0x81); // Text frame flag
            out.write(messageBytes.length); // Payload length
            out.write(messageBytes); // Raw payload
            out.flush();
            
            System.out.println("[Sent Frame] Transmitted Hello frame. Keeping socket open...");
            
            // Hold socket open to prevent immediate termination
            Thread.sleep(10_000);
            System.out.println("[Socket Closing] Timeout reached.");

        } catch (Exception e) {
            System.err.println("Error processing client connection: " + e.getMessage());
        } finally {
            try {
                client.close();
            } catch (IOException e) {
                // ignore
            }
        }
    }

    private static void sendBadRequest(OutputStream out) throws IOException {
        String response = "HTTP/1.1 400 Bad Request\r\nContent-Type: text/plain\r\n\r\nUpgrade to WebSockets required.";
        out.write(response.getBytes(StandardCharsets.US_ASCII));
        out.flush();
    }
}
```

## 7. Common Mistakes & Debugging Scenarios

### Scenario A: Handshake Rejection due to Base64 Key Padding
* **The Problem**: A developer implements custom handshakes in a Java gateway. The connection succeeds in Chrome, but fails when connecting via native Java clients, throwing `HTTP 400 Bad Request`.
* **Why it happens**: When parsing the client `Sec-WebSocket-Key` header, the developer did not call `.trim()` on the key string. The header string contains leading or trailing spaces (e.g. ` dGhlIHNhbXBsZSBub25jZQ==`). Hashing the string with spaces creates a different SHA-1 byte digest, resulting in an incorrect `Sec-WebSocket-Accept` signature. Chrome is forgiving and strips spaces, but strict proxies reject it.
* **The Fix**: Always call `.trim()` when extracting headers.

### Scenario B: CSRF Vulnerability (Cross-Site WebSocket Hijacking)
* **The Problem**: A security audit flags a Spring Boot WebSocket application for Cross-Site WebSocket Hijacking. An attacker can host an iframe on `evil.com` that opens a WebSocket to `bank.com`, accessing the user's session without authorization.
* **Why it happens**: The application did not configure CORS settings or allowed origins on the WebSocket endpoint, accepting all incoming upgrade requests.
* **The Fix**: Configure the WebSocket configuration class in Spring to allow only trusted origins:
  ```java
  @Override
  public void registerWebSocketHandlers(WebSocketHandlerRegistry registry) {
      registry.addHandler(myHandler(), "/ws")
              .setAllowedOrigins("https://bank.com"); // Rejects evil.com during handshake
  }
  ```

## 8. Technical Interview Questions

### Question 1: WebSocket Handshake Signature
*Why does the WebSocket handshake use SHA-1 and Base64 hashing on a random key? Why not just return the key unchanged?*

**Answer**:
The `Sec-WebSocket-Key` hashing is not for encryption; it is to prevent **caching proxies** from misbehaving. 

If a client sends standard HTTP headers, a caching proxy along the path might cache the response. If the client tries to upgrade the protocol, a non-websocket proxy might return a cached `101 Switching Protocols` response from its disk without forwarding the upgrade request to the backend. By forcing the server to calculate a unique signature based on a random client key and a standard GUID, the proxy cannot cache the response, ensuring that the upgrade handshake only succeeds if the backend server actively supports the protocol.

---

### Question 2: Extended CONNECT over HTTP/2
*How does bootstrapping WebSockets over HTTP/2 (RFC 8441) improve performance compared to WebSockets over HTTP/1.1?*

**Answer**:
In HTTP/1.1, the WebSocket handshake hijacks the underlying TCP socket. To open a new WebSocket channel, the client must open a new TCP connection, incurring connection setup costs (TCP and TLS handshakes).

In HTTP/2, RFC 8441 defines an **Extended CONNECT** handshake. Instead of upgrading the TCP connection, the client opens a new logical stream inside an active HTTP/2 connection. It sends a `CONNECT` method request with `:protocol = websocket`. The WebSocket data is encapsulated inside standard HTTP/2 `DATA` frames. This allows multiplexing multiple WebSocket channels over a single TCP connection, eliminating connection setup latency and reducing header overhead via HPACK compression.

## Summary
- **The Upgrade Mechanism** allows WebSockets to reuse port 80 and 443, ensuring compatibility with standard network security devices.
- **The Handshake Signature** concatenates the client key with a standard GUID, computes the SHA-1 hash, and Base64-encodes the result.
- **HTTP/2 extended CONNECT (RFC 8441)** multiplexes multiple WebSocket streams over a single TCP link, eliminating connection setup overhead.
- **HTTP/3 extended CONNECT** operates over QUIC streams, preventing Head-of-Line blocking.
- **Handshake Security** requires validating the `Origin` header to prevent Cross-Site WebSocket Hijacking (CSWSH).
