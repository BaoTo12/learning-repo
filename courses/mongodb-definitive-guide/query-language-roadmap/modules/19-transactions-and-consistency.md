# Module 19: Transactions and Consistency

In this module, we will explore multi-document transactions and consistency controls in MongoDB using MongoDB Compass. While MongoDB guarantees atomic single-document updates, complex enterprise workflows (such as ledger transfers or checkout processes) require multi-document consistency. You will learn the mechanics of BSON ClientSessions, causal consistency, multi-document ACID transactions, replication read concerns (`local`, `majority`, `linearizable`, `snapshot`), write concerns (`w:1`, `w:majority`, `j:true`), and consistency-latency trade-offs.

---

## 1. ACID Transactions & Client Sessions

In relational databases (RDBMS), transactions are started implicitly or explicitly via text SQL blocks. In MongoDB, transactions are managed programmatically via **Client Sessions** and raw database commands passed with a Logical Session ID (`lsid`).

### ACID Concepts in MongoDB:
*   **Atomicity**: Either all write operations inside the transaction succeed and commit, or they all abort and roll back.
*   **Consistency**: Data modified by a transaction must comply with all collection schemas and JSON validation rules.
*   **Isolation**: MongoDB supports **Read Committed** isolation level. Operations inside a transaction are not visible to concurrent readers outside the transaction until it commits.
*   **Durability**: Once a transaction commits with a majority write concern, its modifications are permanently recorded in replica set oplogs and disk journals, surviving server crashes.

## 2. Execution Mechanics (Raw Database Commands)

To run operations inside a transaction, the client or MongoDB Shell generates a Logical Session ID (`lsid`) and associates it with every database command.

### Step 1: Start Session and Transaction
The first write command in the transaction includes the `lsid` along with transaction initialization flags:
```json
{
  "update": "users",
  "updates": [
    {
      "q": { "_id": 101 },
      "u": { "$inc": { "balance": -100 } }
    }
  ],
  "lsid": { "id": { "$uuid": "d4e2f4f2-951b-4f9a-8e2b-ff220023a1a1" } },
  "txnNumber": 1,
  "startTransaction": true,
  "autocommit": false,
  "readConcern": { "level": "snapshot" }
}
```

### Step 2: Subsequent Operations
Subsequent operations in the same transaction reference the same session and transaction number:
```json
{
  "insert": "ledger",
  "documents": [
    { 
      "userId": 101, 
      "amount": -100, 
      "type": "DEBIT", 
      "date": { "$date": "2026-06-15T12:00:00Z" } 
    }
  ],
  "lsid": { "id": { "$uuid": "d4e2f4f2-951b-4f9a-8e2b-ff220023a1a1" } },
  "txnNumber": 1,
  "autocommit": false
}
```

### Step 3: Commit the Transaction
To persist the changes, execute the `commitTransaction` command:
```json
{
  "commitTransaction": 1,
  "lsid": { "id": { "$uuid": "d4e2f4f2-951b-4f9a-8e2b-ff220023a1a1" } },
  "txnNumber": 1,
  "autocommit": false,
  "writeConcern": { "w": "majority" }
}
```

### Alternative: Aborting the Transaction
If an error occurs, roll back the changes by running the `abortTransaction` command:
```json
{
  "abortTransaction": 1,
  "lsid": { "id": { "$uuid": "d4e2f4f2-951b-4f9a-8e2b-ff220023a1a1" } },
  "txnNumber": 1,
  "autocommit": false
}
```

### Causal Consistency Sessions
MongoDB supports **Causal Consistency** within client sessions. If you enable causal consistency, the driver automatically tracks the logical timestamp of operations (`clusterTime`) and guarantees:
*   **Read-Your-Writes**: A read operation in the session is guaranteed to reflect the changes made by a preceding write operation.
*   **Monotonic Reads**: Read queries will never return older data than what was observed in a previous read within the same session.
*   **Monotonic Writes**: Outbound writes are guaranteed to be serialized in the order they were executed.
*   **Writes-Follow-Reads**: If a query observes a state, any subsequent write in the session is ordered after that query.

#### Enabling Causal Consistency (Mongosh Shell in Compass)
In the embedded MongoDB Shell at the bottom of MongoDB Compass, you can run:
```javascript
const session = db.getMongo().startSession({ causalConsistency: true });
```

### Transaction Limits & Constraints:
1.  **Lifetime Limit (`transactionLifetimeLimitSeconds`)**: By default, transactions are restricted to a maximum execution duration of **60 seconds**. If the transaction runs longer, the database coordinator automatically aborts it.
2.  **Size Limit (16MB)**: The total size of all oplog records generated by a single transaction cannot exceed the BSON document limit of **16MB**.

## 3. Read Concerns

Replication read concerns specify what data is visible to a read query across a replica set.

### A. `local` / `available`
*   **Description**: Returns the most recent data written to the node receiving the query.
*   **Behavior**: It does **not** check if the data has been replicated to other members. If the primary node crashes after writing local data but before replication completes, this data can be **rolled back** and deleted. Local read concern is fast but prone to dirty reads.
*   **Default**: `local` is the default read concern.

### B. `majority`
*   **Description**: Returns data that has been acknowledged by a majority of members in the replica set.
*   **Behavior**: Majority-committed data is guaranteed to never be rolled back.
*   **Systems Overhead**: The primary node maintains a snapshot of majority-committed data in cache memory. Queries using `majority` read from this memory snapshot, which adds slight caching overhead.

### C. `linearizable`
*   **Description**: Returns data committed by a majority of replica set members, but verifies that the primary node is still the true primary by sending concurrent heartbeat checks to other members before returning the response.
*   **Behavior**: Protects against split-brain scenarios where a partitioned primary continues serving reads. It has the highest read latency because it blocks on consensus checks.

### D. `snapshot`
*   **Description**: Returns data matching a specific point-in-time snapshot of majority-committed data.
*   **Behavior**: Only available **inside multi-document transactions**. It guarantees repeatable reads across all operations inside the transaction session.

## 4. Write Concerns

Write concerns specify the level of acknowledgment requested from MongoDB for write operations.

### A. `w:1` (Acknowledged Write)
*   **Description**: The write is acknowledged once the primary node applies the modification to its memory cache.
*   **Risk**: If the primary crashes before replicating the write to secondaries, the data is lost.

### B. `w:majority` (Safe Write)
*   **Description**: The write is acknowledged only after it has been replicated to a majority of replica set members (e.g. 2 out of 3 nodes).
*   **Benefit**: Guarantees the write cannot be rolled back during failovers. Highly recommended for financial transactions and primary user records.

### C. `w:0` (Unacknowledged Write)
*   **Description**: Fire-and-forget. The driver returns success immediately after sending the socket packet. 
*   **Risk**: The application cannot detect duplicate key violations, validation errors, or network dropouts. Do not use this in production.

### D. Journaling (`j:true` vs. `j:false`)
MongoDB writes modifications to a memory cache and appends them to a sequential **Journal file** on disk before writing to data files.
*   **`j:true`**: The write is acknowledged only after the node commits the operation to the disk journal. This guarantees durability in the event of a total power loss.
*   **`j:false`**: The write is acknowledged once written to memory. If the node loses power before the journal buffer flush (which occurs every 50ms), the write is lost.

#### The `wtimeout` Configuration
*   If you request `w:majority`, you should also define `wtimeoutMS` (e.g. `wtimeout: 5000`). If replication takes longer than the timeout (e.g. due to node dropouts), the write returns a **Write Concern Error**.
*   **Warning**: Even if a write concern times out, the write may still eventually succeed on the primary node. Designing operations to be **idempotent** is essential to handle write timeouts.

## 5. Consistency vs. Latency Trade-offs

Choosing read and write concern configurations dictates your system's position on the CAP theorem spectrum.

### Trade-off Matrix

| Level | Read Concern | Write Concern | Durability | Latency | Use Case |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Low Consistency** | `"local"` | `w:1` | **Low**. Prone to rollbacks. | **Sub-millisecond**. | Analytics events, session tracking, page view counters. |
| **Balanced** | `"majority"` | `w:majority` | **High**. Replicated to majority. | Medium (dependent on network replication). | Standard user profiles, order processing, catalogs. |
| **Strict Consistency** | `"linearizable"` | `w:majority` / `j:true` | **Maximum**. Committed to disk on majority. | **High**. Blocks on disk I/O and replica heartbeats. | Financial ledgers, security configurations, primary keys. |
