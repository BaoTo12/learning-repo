To build production-grade real-time systems, an engineer must look past basic library wrappers and understand the protocol under the hood. A WebSocket does not appear out of thin air; it begins as a standard HTTP transaction and undergoes a structured upgrade handshake before switching to a binary framing layer.

## 1. The HTTP Upgrade Mechanism

When a browser client attempts to establish a WebSocket connection to a server (e.g. `ws://api.example.com/stream`):
- The browser cannot immediately send binary WebSocket frames.
- It does not know if the target server, or any intermediate proxy, firewalls, or load balancers along the route support the WebSocket protocol.
- If the browser sent raw binary frames immediately, standard HTTP proxies would misinterpret the traffic as malformed HTTP, log errors, and terminate the connection.

### Switching Protocols (The Upgrade Path)
To prevent proxy blocks, the protocol reuse pattern is applied:
1. The connection begins as a standard, valid HTTP/1.1 GET request.
2. The client includes headers requesting to upgrade the protocol state.
3. Intermediate proxies parse the request headers. If they support WebSockets, they pass the request along. If they do not, they return an error (e.g., `400 Bad Request` or `501 Not Implemented`), letting the client fallback to polling.
4. If the server accepts the upgrade, it returns an HTTP response confirming the switch.
5. The TCP socket is hijacked: the HTTP parsing engines on both client and server are disabled, and the connection switches to the WebSocket binary framing layer.

## 2. Anatomy of the HTTP/1.1 Handshake

Let us analyze the raw request and response headers exchanged during connection setup.

### The Client Handshake Request
The client initiates connection setup by sending an HTTP GET request containing upgrade headers:

```http
GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: http://example.com
Sec-WebSocket-Protocol: chat, superchat
Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits
```

#### Client Headers Explained:
- **`Upgrade: websocket`**: The primary header instructing the server to switch from HTTP to the WebSocket protocol framing engine.
- **`Connection: Upgrade`**: Notifies intermediate routers that this connection should be kept active and upgraded, rather than closed after the response is completed.
- **`Sec-WebSocket-Key`**: A random 16-byte base64-encoded value generated by the browser for each connection. This key is used by the server to calculate a validation signature.
- **`Sec-WebSocket-Version`**: Specifies the protocol version (RFC 6455 requires version `13`).
- **`Origin`**: Declares the origin domain of the script requesting the connection. The server inspects this header to enforce CORS policies and protect against Cross-Site WebSocket Hijacking.
- **`Sec-WebSocket-Protocol`**: A comma-separated list of application-level subprotocols the client supports (e.g., `chat`, `stomp`, `wamp`). The server selects one and returns it.
- **`Sec-WebSocket-Extensions`**: Lists optional extensions the client supports, such as payload compression (`permessage-deflate`).

---

### The Server Handshake Response
If the server accepts the upgrade, it responds with:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: chat
Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits
```

#### Server Headers Explained:
- **`HTTP/1.1 101 Switching Protocols`**: The standard HTTP status code indicating the server is switching to the protocol requested in the upgrade header.
- **`Sec-WebSocket-Accept`**: Proven confirmation that the server successfully upgraded the connection. It contains a cryptographic signature calculated from the client's key, confirming the server supports WebSockets.
- **`Sec-WebSocket-Protocol`**: The single subprotocol selected by the server (e.g., `chat`).
- **`Sec-WebSocket-Extensions`**: The extensions accepted by the server.

## 3. Cryptographic Validation Mechanics

The `Sec-WebSocket-Key` and `Sec-WebSocket-Accept` headers are not used to encrypt data or authenticate clients. Instead, they are used to **prevent caching proxy servers from misrouting old connection cache results**.

### Why the Validation Key Exists
In the early days of the web, caching proxies often cached HTTP responses.
- If a server returned a page on a path, the proxy cached it and returned it to subsequent clients.
- If a WebSocket connection was opened on that path, a non-WebSocket proxy might cache the `101 Switching Protocols` response.
- When a different client subsequently requests standard HTTP from that path, the proxy might return the cached `101` response, causing the client browser to crash.
- Enforcing a unique cryptographic handshake signature ensures that caching proxies cannot cache or reuse these responses.

### Hashing Formula
According to RFC 6455 Section 1.3, the server calculates the accept signature using the following steps:
1. Get the client's `Sec-WebSocket-Key` string (e.g., `"dGhlIHNhbXBsZSBub25jZQ=="`).
2. Append the globally unique RFC 6455 Magic GUID string:
   `"258EAFA5-E914-47DA-95CA-C5AB0DC85B11"`
3. Calculate the SHA-1 hash of this combined string.
4. Base64-encode the raw SHA-1 digest bytes.

### Step-by-Step Mathematical Walkthrough
Let us trace the accept hash calculation using the client key from the RFC example:

1. **Client Key**: `dGhlIHNhbXBsZSBub25jZQ==`
2. **Append GUID**: Append the magic GUID string:
   `"dGhlIHNhbXBsZSBub25jZQ==258EAFA5-E914-47DA-95CA-C5AB0DC85B11"`
3. **Calculate SHA-1 Hash**: Calculate the SHA-1 hash of the combined string bytes:
   - Output (Hex): `b37a4f2c135690f64606cc7b671a7ec4eacdec2a`
   - Output (Binary Bytes): `[179, 122, 79, 44, 19, 86, 144, 246, 70, 6, 204, 123, 103, 26, 126, 196, 234, 205, 236, 42]`
4. **Base64 Encode**: Base64-encode the 20-byte digest.
   - Result: `"s3pPLMBiTxaQ9kYGzzhZRbK+xOo="`
5. **Verify**: This matches the `Sec-WebSocket-Accept` header returned in the server response.

---

### Go Implementation
Below is a standalone Go program showing how to calculate the accept key using standard Go packages `crypto/sha1` and `encoding/base64`:

```go
package main

import (
	"crypto/sha1"
	"encoding/base64"
	"fmt"
)

const MagicGUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"

// ComputeAcceptKey calculates the Sec-WebSocket-Accept signature
func ComputeAcceptKey(challengeKey string) string {
	// 1. Concatenate the key with the magic GUID string
	combined := challengeKey + MagicGUID

	// 2. Compute the SHA-1 digest
	hasher := sha1.New()
	hasher.Write([]byte(combined))
	sha1Sum := hasher.Sum(nil)

	// 3. Base64-encode the raw SHA-1 bytes
	return base64.StdEncoding.EncodeToString(sha1Sum)
}

func main() {
	clientKey := "dGhlIHNhbXBsZSBub25jZQ=="
	expectedAccept := "s3pPLMBiTxaQ9kYGzzhZRbK+xOo="
	
	computedAccept := ComputeAcceptKey(clientKey)
	
	fmt.Println("=== Sec-WebSocket-Accept Hash Calculator ===")
	fmt.Println("Client Key     :", clientKey)
	fmt.Println("Expected Accept:", expectedAccept)
	fmt.Println("Computed Accept:", computedAccept)
	
	if computedAccept == expectedAccept {
		fmt.Println("Result         : SUCCESS (Signature matches!)")
	} else {
		fmt.Println("Result         : FAILURE (Signature mismatch!)")
	}
}
```

## 4. Modern HTTP Protocol Upgrades (HTTP/2 & HTTP/3)

Under HTTP/1.1, the upgrade handshake hijacks the underlying TCP connection, taking exclusive control of the socket.

Under **HTTP/2 (RFC 8441)**, this model is different:
- HTTP/2 multiplexes multiple independent request streams over a single TCP connection.
- If a WebSocket connection hijacked the underlying TCP connection under HTTP/2, it would break all other active streams sharing that connection.

### Bootstrapping WebSockets over HTTP/2 (RFC 8441)
RFC 8441 solves this by using an extended **`CONNECT`** request instead of the standard GET request:

```http
CONNECT /chat HTTP/2
Host: server.example.com
:method: CONNECT
:protocol: websocket
:scheme: https
:path: /chat
:authority: server.example.com
sec-websocket-version: 13
sec-websocket-protocol: chat
```

- **`:method: CONNECT`**: Uses the CONNECT method to establish a tunnel stream.
- **`:protocol: websocket`**: The new pseudo-header indicating the target protocol is WebSocket.
- **`sec-websocket-key`**: **Not used** under HTTP/2 because the connection runs inside an active HTTP/2 stream, which is immune to HTTP/1.1 caching proxy caching issues.

Once the stream returns `:status: 200`, the connection switches to the WebSocket framing layer. The WebSocket frames are wrapped inside standard HTTP/2 `DATA` frames.

---

### Bootstrapping WebSockets over HTTP/3 (RFC 9220)
In **HTTP/3 (RFC 9220)**, WebSockets are negotiated similarly:
- Uses the extended `CONNECT` method over the QUIC transport layer (which runs over UDP).
- Enables the HTTP/3 settings parameter `SETTINGS_ENABLE_CONNECT_PROTOCOL` to notify the client that the server supports upgrades.
- Multiplexes WebSockets natively inside QUIC stream allocations. If one stream suffers packet loss, other streams continue running, preventing Head-of-Line blocking entirely.

### Upgrade Protocol Matrix

| Protocol Version | Transport Layer | Handshake Method | Connection Hijacking? | Multiple Sockets over 1 TCP? |
| :--- | :--- | :--- | :--- | :--- |
| **HTTP/1.1** | TCP | HTTP GET Upgrade | Yes (Exclusive socket) | No |
| **HTTP/2 (RFC 8441)** | TCP | Extended CONNECT | No (Stream tunnel) | Yes (Multiplexed) |
| **HTTP/3 (RFC 9220)** | UDP (QUIC) | Extended CONNECT | No (Stream tunnel) | Yes (Multiplexed) |

## 5. Connection Hijacking in Go Servers

In Go, when you start a standard HTTP server using `http.ListenAndServe`, the server runtime manages the TCP socket connections, parses incoming HTTP headers, and delegates routing to registered handler functions.

When upgrading to a WebSocket connection, you must claim ownership of the underlying TCP socket. This is accomplished using **Connection Hijacking**.

### The `http.Hijacker` Interface
The standard Go `net/http` package defines the `Hijacker` interface:

```go
package http

import (
	"bufio"
	"net"
)

type Hijacker interface {
	// Hijack lets the caller take over the connection.
	// It returns the raw TCP connection, a buffered reader/writer, and an error.
	Hijack() (net.Conn, *bufio.ReadWriter, error)
}
```

---

### Custom Upgrader: Writing an Upgrade Handshake from Scratch in Go

To understand how a WebSocket library works internally, let us build a basic connection upgrader from scratch without using any external dependencies.

This implementation asserts the `http.ResponseWriter` as an `http.Hijacker`, takes control of the socket, reads the request headers, calculates the `Sec-WebSocket-Accept` hash, and writes the `101 Switching Protocols` handshake response:

```go
package main

import (
	"bufio"
	"crypto/sha1"
	"encoding/base64"
	"fmt"
	"log"
	"net"
	"net/http"
	"strings"
)

const magicGUID = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"

func manualUpgradeHandler(w http.ResponseWriter, r *http.Request) {
	// 1. Verify that the client requested a WebSocket upgrade
	if r.Header.Get("Upgrade") != "websocket" || !strings.Contains(r.Header.Get("Connection"), "Upgrade") {
		http.Error(w, "Upgrade headers missing", http.StatusBadRequest)
		return
	}

	// 2. Extract the challenge key
	clientKey := r.Header.Get("Sec-WebSocket-Key")
	if clientKey == "" {
		http.Error(w, "Sec-WebSocket-Key missing", http.StatusBadRequest)
		return
	}

	// 3. Compute the accept validation hash
	combined := clientKey + magicGUID
	hasher := sha1.New()
	hasher.Write([]byte(combined))
	acceptKey := base64.StdEncoding.EncodeToString(hasher.Sum(nil))

	// 4. Type assert the ResponseWriter to http.Hijacker
	hijacker, ok := w.(http.Hijacker)
	if !ok {
		http.Error(w, "Web server does not support connection hijacking", http.StatusInternalServerError)
		return
	}

	// 5. Hijack the connection: take over the raw TCP socket
	conn, readWriter, err := hijacker.Hijack()
	if err != nil {
		http.Error(w, err.Error(), http.StatusInternalServerError)
		return
	}
	defer conn.Close() // Ensure the TCP socket is closed when the handler exits

	log.Println("[Server] Connection hijacked successfully!")

	// 6. Write the raw HTTP 101 response bytes directly to the TCP write buffer
	responseHeaders := fmt.Sprintf(
		"HTTP/1.1 101 Switching Protocols\r\n"+
			"Upgrade: websocket\r\n"+
			"Connection: Upgrade\r\n"+
			"Sec-WebSocket-Accept: %s\r\n\r\n",
		acceptKey,
	)
	
	_, err = readWriter.WriteString(responseHeaders)
	if err != nil {
		log.Println("[Server] Failed to write handshake response:", err)
		return
	}
	readWriter.Flush() // Flush buffer to send headers to the client immediately

	log.Println("[Server] Handshake completed! Sockets switched to framing mode.")

	// 7. Enter the frame processing loop (reading raw bytes)
	processRawFrames(conn, readWriter.Reader)
}

func processRawFrames(conn net.Conn, reader *bufio.Reader) {
	for {
		// Read the first 2 bytes of the WebSocket frame
		headerBytes := make([]byte, 2)
		_, err := io.ReadFull(reader, headerBytes)
		if err != nil {
			log.Println("[Server] Client disconnected:", err)
			break
		}

		fin := (headerBytes[0] & 0x80) != 0
		opcode := headerBytes[0] & 0x0F
		masked := (headerBytes[1] & 0x80) != 0
		payloadLen := int(headerBytes[1] & 0x7F)

		log.Printf("[Server Frame Reader] FIN: %t | Opcode: 0x%X | Masked: %t | Payload Len: %d bytes\n", 
			fin, opcode, masked, payloadLen)

		// If the frame is a Close request, terminate the loop
		if opcode == 0x8 {
			log.Println("[Server] Close frame received. Terminating socket.")
			break
		}
		
		// For simplicity, skip parsing the masking key and payload data.
		// In a production upgrader, you must read the masking key (4 bytes) and decode the payload.
	}
}
```

## 7. Common Mistakes & Reverse Proxy Tuning

### Scenario A: CORS Handshake Rejections (`403 Forbidden`)
* **The Problem**: You deploy your Go server to production (`api.example.com`), and configure your web frontend (`app.example.com`) to establish a WebSocket connection. During setup, the handshake fails, returning `HTTP 403 Forbidden` errors.
* **Why it happens**: By default, Gorilla's `websocket.Upgrader` enforces strict CORS checks. If the client origin domain (`app.example.com`) does not match the server domain (`api.example.com`), the upgrader rejects the handshake.
* **The Fix**: Configure the upgrader's `CheckOrigin` function to whitelist your client domains:
  ```go
  var upgrader = websocket.Upgrader{
      CheckOrigin: func(r *http.Request) bool {
          origin := r.Header.Get("Origin")
          return origin == "https://app.example.com"
      },
  }
  ```

### Scenario B: Nginx Stripping Upgrade Headers
* **The Problem**: A Go application runs fine locally, but fails when deployed behind an Nginx reverse proxy. The client console throws `WebSocket Handshake failed: Connection closed before receiving 101` errors.
* **Why it happens**: By default, Nginx terminates connection headers. If not configured correctly, it strips the `Upgrade` and `Connection` headers before forwarding the request to the Go application.
* **The Fix**: Update your Nginx server block to explicitly forward the upgrade headers:
  ```nginx
  location /ws {
      proxy_pass http://localhost:8080;
      proxy_http_version 1.1;
      proxy_set_header Upgrade $http_upgrade;
      proxy_set_header Connection "Upgrade";
      proxy_set_header Host $host;
  }
  ```

## 8. Technical Interview Questions

### Question 1: Why does `Sec-WebSocket-Key` exist?
*Why does the WebSocket protocol require a handshake key? Does it encrypt the payload?*

**Answer**:
The `Sec-WebSocket-Key` does **not** encrypt the payload or authenticate the client. 

Its sole purpose is to prevent caching proxy servers from misrouting old connection cache results. 

By requiring the server to calculate a unique SHA-1 accept signature from the client's key, the browser can verify the server supports WebSockets, preventing caching proxies from caching or reusing the response.

---

### Question 2: Raw TCP Sockets vs. WebSockets in Browser
*Why don't web browsers allow JavaScript to open raw TCP sockets directly? What security purpose do WebSockets serve?*

**Answer**:
Letting JavaScript open raw TCP sockets would create major security vulnerabilities, allowing malicious scripts to send spam emails via SMTP or access local networks. 

WebSockets provide a secure abstraction layer. The browser controls connection establishment, enforces CORS origin rules, and requires client frames to be masked to prevent cache-poisoning attacks on intermediate proxies.

---

### Question 3: Gorilla Upgrader Origin Checking
*Explain how Gorilla's `websocket.Upgrader` verifies the client's origin. What happens if you return `true` inside `CheckOrigin`?*

**Answer**:
The upgrader reads the `Origin` header from the handshake request. By default, it compares the origin domain to the target server's host domain. If they do not match, it returns `HTTP 403 Forbidden`. 

If you configure `CheckOrigin` to always return `true`:
```go
CheckOrigin: func(r *http.Request) bool { return true }
```
The server permits connections from **any origin**, exposing the application to Cross-Site WebSocket Hijacking (CSWSH) if you rely solely on cookies for authentication.

---

### Question 4: RFC 8441 WebSocket over HTTP/2
*How does RFC 8441 change the WebSocket upgrade process under HTTP/2 compared to HTTP/1.1?*

**Answer**:
Under HTTP/1.1, the upgrade handshake hijacks the underlying TCP connection. 

Under HTTP/2, this would break all other multiplexed streams sharing that connection. 

RFC 8441 resolves this by using an extended **`CONNECT`** request with a `:protocol: websocket` pseudo-header. This establishes a WebSocket tunnel inside an active HTTP/2 stream, allowing WebSockets to run alongside standard HTTP requests over a single TCP connection.

---

### Question 5: What is Connection Hijacking in Go?
*What does the Go `http.Hijacker` interface accomplish during a WebSocket upgrade?*

**Answer**:
The `http.Hijacker` interface allows a handler to take over the underlying connection. 

Calling `Hijack()` returns the raw TCP connection (`net.Conn`) and a buffered reader/writer (`*bufio.ReadWriter`), detaching the socket from Go's standard HTTP server engine. The upgrader can then write the `HTTP 101` response directly to the buffer and switch to the WebSocket framing engine.

---

### Question 6: HTTP 101 Switching Protocols
*What is the meaning of the HTTP 101 status code during the WebSocket handshake?*

**Answer**:
The `HTTP 101 Switching Protocols` status code is returned by the server to confirm it accepts the client's request to upgrade the connection. 

When this code is returned, the client and server stop parsing data as HTTP text requests/responses. The underlying TCP connection is kept open, and the communication format switches to the binary WebSocket framing protocol.

---

### Question 7: Why is SHA-1 used in the handshake calculation if it is deprecated for security?
*Since SHA-1 is vulnerable to collision attacks, why does RFC 6455 specify it for calculating the accept hash?*

**Answer**:
The accept hash is not used to secure the connection or authenticate the client. 

Its sole purpose is to prove to the browser that the server supports WebSockets, preventing caching proxies from returning cached responses. 

Since it does not serve a security or cryptographic protection purpose, the speed of SHA-1 is preferred over more secure, but computationally expensive algorithms like SHA-256.

---

### Question 8: How do Reverse Proxies (like Nginx) handle WebSocket handshakes?
*What headers must be explicitly configured in a reverse proxy to support WebSocket upgrades?*

**Answer**:
By default, reverse proxies terminate connection headers. To support WebSockets, you must configure the proxy to forward the upgrade headers:
- `Upgrade`: Must be set to `$http_upgrade` (typically `"websocket"`).
- `Connection`: Must be set to `"Upgrade"`.
This instructs the proxy to keep the TCP socket open and act as a blind relay forwarding frames.

---

### Question 9: Why are client frames masked but server frames are not?
*What security threat does masking prevent?*

**Answer**:
Masking prevents cache-poisoning attacks on intermediate proxies. 

If a client sends an unmasked frame containing HTTP request headers inside the WebSocket payload, an intermediate proxy might misinterpret the payload bytes as a new HTTP request, caching malicious content. 

Masking scrambles the payload bytes on the wire using a random 4-byte key, preventing proxies from recognizing pattern strings. Server frames do not need masking because client browsers are not shared caching intermediaries.

---

### Question 10: How does connection hijacking affect Go middleware?
*Why do logging or Gzip compression middleware fail or behave unexpectedly when applied to WebSocket endpoints in Go?*

**Answer**:
Go middleware typically wraps the `http.ResponseWriter` to log metrics or compress the response bytes. 

When a WebSocket handler calls `Hijack()`, it takes over the underlying TCP connection and detaches the socket from the HTTP server engine. 

As a result, any middleware wrapping the writer is bypassed, and attempts to write bytes to the hijacked response writer will throw panic errors or fail silently.

## Summary
- **Protocol Upgrades** transition active port connections from text-based stateless parsing to binary stateful frame streams.
- **The HTTP/1.1 Handshake** uses `Upgrade: websocket`, `Connection: Upgrade`, and a random `Sec-WebSocket-Key` to negotiate connection setup.
- **The Accept Key** is calculated using SHA-1 and Base64 algorithms to prevent caching proxies from misrouting requests.
- **RFC 8441 and RFC 9220** enable WebSockets over HTTP/2 and HTTP/3 using extended `CONNECT` requests, allowing multiplexing without opening separate TCP connections.
- **Go Connection Hijacking** uses `http.Hijacker` to claim ownership of the underlying TCP socket, detaching it from Go's standard HTTP server engine.
- **Manual Inspection** using browser DevTools allows capturing handshakes and viewing text/binary frames in real-time.
